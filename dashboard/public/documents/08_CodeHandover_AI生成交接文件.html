3. 核心 API Route 邏輯摘要

3.1 anomalies/route.ts — 最複雜的核心邏輯

此 API 是系統智能的核心，主要流程：

  1. 從 Settings 讀取當前門檻參數（pm25_threshold, consecutive_exceeds, cluster_radius_km, min_cluster_stations）
  2. 依據 consecutive_exceeds 值，查詢過去 N 個 5 分鐘桶的觀測資料
  3. 對每個測站執行「連續 N 筆超標」判定，篩選出種子點集合
  4. 呼叫 buildClusters()，使用 getDistanceKm()（Haversine）進行空間聚合
  5. 立即回傳 clusters（不等待寫入），同時以 fire-and-forget 非同步呼叫 autoCreateEvents() 寫入 DB
⚠️ autoCreateEvents 不使用 await，是刻意設計的非同步解耦。修改此部分時請勿改為 await，否則會讓 API 延遲上升至 2-5 秒。

3.2 events/route.ts — 一次性資料遷移邏輯

在 GET 請求中包含一段一次性的歷史資料清理邏輯（將舊格式事件標題正規化）。這是一種 Lazy Migration 模式（在讀取時順帶修正舊資料），無需額外的資料庫 Migration 腳本。當所有舊資料都已修正後，此段邏輯的比對條件將不再命中，overhead 趨近於零。

5. 環境切換機制說明

每個 API Route 的頂層邏輯均遵循以下三軌模式：

// ── Tier 1: Supabase（Vercel 線上環境）──
if (supabase) {
  const { data } = await supabase.from('table').select('*');
  return NextResponse.json(data);
}

// ── Tier 2: SQLite（本地開發環境）──
const db = await getDb();
if (db) {
  const rows = await db.all('SELECT * FROM table');
  return NextResponse.json(rows);
}

// ── Tier 3: Mock 降級──
return NextResponse.json(globalMockState.defaultData);

這個模式確保在任何環境下 API 都有回應，不會出現 500 錯誤。

6. 已知技術債與未來優化建議

Hack eval require 繞過 Webpack NFT

位置：lib/db.ts:29。使用 eval("require('sqlite3')") 避免 Vercel 打包原生模組。這是已知的工程折衷方案，在本地環境正常運作，但使程式碼可讀性降低。
建議改善：v2.0 考慮改用 better-sqlite3（有官方 Vercel 支援）或完全移除 SQLite，改以環境變數切換純 Mock 模式。

設計 單一帳號密碼認證（無 RBAC）

位置：api/login/route.ts。目前僅支援單一管理員密碼，無角色分級。
建議改善：導入 Supabase Auth 或 NextAuth.js，實現多角色 JWT Token 分級存取控制。

效能 前端 DOM Marker 大量更新

位置：components/Map/SensorMap.tsx。1,100+ 個 DOM Marker 在歷史播放時同步更新，低效能設備可能卡頓。
建議改善：改用 Mapbox GL circle 圖層（WebGL 渲染），以 GeoJSON expression 動態上色，可大幅提升播放流暢度至 60 FPS。

效能 Supabase 無 JOIN 查詢，前端記憶體映射

位置：api/events/route.ts:41。Supabase 模式下 sensors 欄位回傳空陣列，前端透過最近鄰算法反查。
建議改善：在 Supabase 建立 PostgreSQL View 或 RPC Function 執行伺服器端 JOIN。
