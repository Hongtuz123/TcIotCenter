3. 資料表詳細說明

3.1 sensors — 測站基本資料表

靜態主資料，由 pollIoT.ts 首次啟動時 upsert 填充，後續更新頻率極低。

欄位型別屬性說明
station_idTEXTPRIMARY KEY環境部唯一設備代號（如 TC0062）
device_nameTEXTNOT NULL設備名稱（如 大里國中）
latDOUBLE PRECISIONNOT NULL緯度（WGS84）
lonDOUBLE PRECISIONNOT NULL經度（WGS84）
cityTEXTDEFAULT '臺中市'縣市名稱
townshipTEXT可為 NULL行政區（如 大里區）
areaTEXT可為 NULL工業區名稱（如 大里產業園區）
area_typeTEXT可為 NULLareaType（工業區 / 一般）
created_atTIMESTAMPTZDEFAULT NOW()建立時間
updated_atTIMESTAMPTZAUTO TRIGGER自動觸發器維護更新時間

3.2 observations_5m — 5分鐘聚合觀測值表

核心時序資料表，每 5 分鐘由 Poller 寫入。資料保留 7 天，由 cleanup_old_observations() 定期清理。

欄位型別屬性說明
idBIGSERIALPRIMARY KEY自增主鍵
station_idTEXTFK → sensors外鍵（刪除站點時 CASCADE）
bucket_timeTIMESTAMPTZUNIQUE(station_id, bucket_time)5 分鐘對齊時間桶（10:05:00, 10:10:00）
pm2_5DOUBLE PRECISION可為 NULL平均 PM₂.₅ 濃度（µg/m³）
temperatureDOUBLE PRECISION可為 NULL平均溫度（°C）
humidityDOUBLE PRECISION可為 NULL平均相對濕度（%）
pm25_samplesSMALLINTDEFAULT 05分鐘內 PM₂.₅ 原始樣本數（完整率計算用）
is_anomalyBOOLEANDEFAULT FALSE是否被標記為異常（由 API 判定後回寫）
anomaly_typeTEXT可為 NULL異常類型描述
Index 策略：
① UNIQUE idx_obs5m_station_bucket (station_id, bucket_time)：確保同站同時間只有一筆，支援 upsert 操作。
② idx_obs5m_bucket_time (bucket_time DESC)：加速「查詢最新一期資料」的場景。
③ idx_obs5m_station_time (station_id, bucket_time DESC)：加速「單站連續 N 筆歷史查詢」，是連續超標演算法的核心索引。

3.3 events — 群聚事件表

由 /api/anomalies 非同步自動建立，或系統管理員手動建立。

欄位型別屬性說明
idTEXTPRIMARY KEY格式：auto_{YYYYMMDDHHMM}_{lat.3f}_{lon.3f}
titleTEXTNOT NULL標準格式：[自動] 微感事件 (門檻: PM₂.₅ XX)
descriptionTEXT-詳細說明（超標站數、平均濃度、主導類型）
statusTEXTDEFAULT '待確認'可為：待確認 / 調查中 / 已結案
boundsTEXT (JSON)-儲存為 JSON 字串：{"center":{"lat":...,"lon":...},"radiusKm":...}
event_timeTEXT-事件觸發的觀測時間點（非建立時間）
stations_countINTEGER-超標測站總數
avg_pm25DOUBLE / REAL-群聚圈內測站的平均 PM₂.₅ 濃度
dominant_typeTEXT-群聚中最多測站的異常類型
created_atTIMESTAMPTZDEFAULT NOW()事件建立時間
updated_atTIMESTAMPTZDEFAULT NOW()最後更新時間

3.4 completeness_log — 完整率快照表

欄位型別說明
idBIGSERIAL自增主鍵
snapshot_timeTIMESTAMPTZ快照計算時間
window_start / window_endTIMESTAMPTZ統計視窗的開始與結束時間
total_sensorsINT當前台中總站數
expected_obsINT預期筆數（total_sensors × 12，每小時每站 12 筆）
actual_obsINT實際有資料的站×時間點數
completeness_rateDOUBLE PRECISIONactual_obs / expected_obs，0.0 ~ 1.0
offline_countINT連續無資料的站點數

4. 自動維護機制

4.1 updated_at 自動觸發器

CREATE OR REPLACE FUNCTION update_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER sensors_updated_at
  BEFORE UPDATE ON sensors
  FOR EACH ROW EXECUTE FUNCTION update_updated_at();

4.2 7 天舊資料清理函式

需另行設定排程呼叫（如 Supabase pg_cron 或外部 Cron Job）：

SELECT cleanup_old_observations();
-- 清除 observations_5m 7 天前資料
-- 清除 completeness_log 30 天前資料
⚠️ 若未設定排程呼叫此函式，observations_5m 資料將無限累積，請務必在生產環境配置定期清理。

5. SQLite 本地環境差異說明

本地 SQLite (iot.db) 使用略有差異的欄位命名（歷史遺留），主要差異如下：

Supabase 欄位SQLite 欄位差異說明
station_idid主鍵名稱不同
device_namename欄位別名不同
observations_5mobservations資料表名稱不同
bucket_timetime時間欄位名稱不同

API 層程式碼已透過條件判斷處理兩套命名差異，對前端透明。
