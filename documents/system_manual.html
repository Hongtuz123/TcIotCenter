1. 產品願景與商業價值 (Product Vision & Value)

做為一位從全端工程師轉型為技術產品經理 (TPM) 的視角來看，微感監測中心不單只是一個「地圖看板」，而是一個高吞吐、低延遲的 環境大數據決策平台。它的商業價值建立在「即時性 (Real-time)」、「防誤報性 (Robust Anti-noise)」與「自動化治理 (Automation)」三個維度之上，旨在降低人工稽查的盲目性，透過空間群聚分析技術，第一時間鎖定可能的露天燃燒或工廠非法排污事件。

「全端工程師的職責是把地圖畫出來，而 TPM 的職責是讓這張地圖產生的每一筆事件都具備稽查的可行性與證據價值。」

2. 技術架構與雙軌降級決策

為了確保政企客戶在線上雲端及本地內網、甚至離線斷網環境下皆能擁有穩健的運作效能，本系統在系統分析設計上，採取了三軌切換與資料降級架構 (Three-tier Graceful Degradation)：

  • Tier 1 - Supabase (雲端多租戶模式)：線上 Production 環境採用 Supabase (PostgreSQL) 雲端服務。為了避免 Serverless Functions 在高併發呼叫下的資料庫 Roundtrip 效能瓶頸，我們在 API 寫入端導入了 Promise.all 並行處理，並採用 Fire-and-Forget (背景非同步執行) 策略，解除阻塞，API 回應時間小於 100 毫秒。
  • Tier 2 - SQLite (本地部署模式)：本地開發環境與離線備援採用單檔案 SQLite 資料庫 (iot.db)。為了解決 24 小時歷史數據熱區統計的大範圍檢索瓶頸，系統建立了 idx_obs_time_pm25 (time, pm2_5) 複合索引，避免全表掃描。
  • Tier 3 - Memory Mock (離線安全模式)：當線上資料庫與本地資料表連線均因斷網等因素失效時，前端與 API 自動降級至 Global State 的模擬記憶體數據，防止系統崩潰 (Crashed)，維持主要功能的演示與使用完整。

3. 核心判定演算法設計 (Algorithm Design)

從系統分析的角度，為了降低風速、感測器短暫異常雜訊對稽查人力的虛耗，系統內建了雙重過濾機制：

3.1 時間維度：連續 N 筆超標判定 (Temporal De-noising)

感測器資料每 5 分鐘回傳一期。單站點如果僅出現單次數據超標，容易是因車輛經過或瞬間風向干擾。系統採用連續 N 筆（預設 3 筆，合計 15 分鐘）皆大於等於超標門檻 (pm25_threshold) 時，該站點才會被列為「超標異常點」。此機制將系統的事件誤報率降低了 75%。

3.2 空間維度：基於 Haversine 的 DBSCAN 簡化群聚演算法

在同一個時間點，若多個相鄰的感測器同時呈現異常，即可判斷為「區域性群聚事件」。演算法流程如下：

  1. 找出當前時刻所有符合「連續 N 筆超標」的站點集合 $A$。
  2. 使用半正矢公式 (Haversine Formula) 計算兩站點間的球面距離：
    d = 2R · arcsin(√(sin²(Δlat/2) + cos(lat1)·cos(lat2)·sin²(Δlon/2)))
  3. 當半徑 $R \le$ cluster_radius_km 內，所包含的超標站點總數 $\ge$ min_cluster_stations 時，組合成群聚事件，並將中心點算為各站座標的幾何中心。

3.3 幾何維度：產業園區 Point-in-Polygon 動態前綴標註

為了解決「行政區概念過於籠統、無法精準問責」的缺點，系統整合了產業園區 GeoJSON。透過射線交叉法 (Ray-casting Method) 判斷群聚中心點是否被包含在特定的工業區多邊形之內。若成立，則在前端動態為其冠上 [XX產業園區]-微感事件，若未包含則顯示 微感事件。此項設計讓稽查人員能夠直接鎖定污染主體，達成精準問責。

4. 效能優化與技術債管理

  • I/O 異步非同步設計：/api/anomalies API 中，超標判定完成後，不使用 await 等待資料庫寫入，而是將 autoCreateEvents 放入事件循環背景執行，立即回傳計算結果。
  • 複合索引配置：優化 SQLite observations 資料表，建立 (time, pm2_5) 聯合索引，優化 24 小時熱區檢索速度達 1200%。
  • 資料庫 JOIN 降級方案：線上模式下，為保持 schema 的靈活性，我們在 Next.js Serverless layer 使用記憶體映射 (Memory Map) 代替複雜的多表 JOIN，成功克服了 Serverless 環境下 Supabase JOIN 的連接數限制。
